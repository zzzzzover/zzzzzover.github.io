# Feature Specification: 个人作品集与技术博客站点

**Feature Branch**: `001-portfolio-blog`

**Created**: 2026-09-12

**Status**: Draft

**Input**: User description: "个人作品集与技术博客站点：展示离职后独立完成的项目与技术文章，支持 Markdown 写作自动发布、项目详情页与可扩展 demo 嵌入"

## 背景

站主在离职后独立完成了若干工程项目并写了若干技术文章，这些内容目前散落在本地目录、代码仓库和文档中，没有对外可访问的入口。站点需要把这些内容汇集到一个可长期维护的地址上，同时服务于两个目的：让招聘方能快速判断站主的能力，让技术读者能读到并订阅内容。

站点存在的前提是**内容已经写好**——它不是创作的起点，而是内容的发布出口。因此"把已有素材搬上去"和"以后加内容足够省事"这两件事，比页面本身的丰富程度重要。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 访客快速认识站主并建立联系 (Priority: P1)

一位招聘方通过简历或社交平台拿到站点地址，在不确定要不要继续了解的情况下打开首页。他希望在不需要滚动、不需要点击任何链接的情况下，就看清这个人是谁、擅长什么、怎么联系。如果这一步没做到，后面的项目和文章都不会被看到。

**Why this priority**: 这是站点最核心的使命——求职作品集的入口。它单独成立就是一个可用的最小站点：即使没有任何项目和文章，一个讲清身份和联系方式的页面也已经能产生价值。

**Independent Test**: 只实现首页与"关于我"页面并对外发布，让一个不了解站主的人打开首页，检验他能否在不追问的情况下说出站主是谁、做什么方向、如何联系。

**Acceptance Scenarios**:

1. **Given** 访客第一次打开首页，**When** 页面加载完成，**Then** 首屏（无需滚动）可见站主身份描述、主要技术方向与至少一种联系方式。
2. **Given** 访客位于首页，**When** 他打开"关于我"页面，**Then** 可见个人简介、技能概览、工作经历、联系方式与公开技术账号。
3. **Given** 访客从任一内页进入，**When** 他想返回首页或联系站主，**Then** 这两个入口在任意页面都可见。

---

### User Story 2 - 访客了解一个项目的完整来龙去脉 (Priority: P2)

一位面试官对站主的某个项目感兴趣，进入该项目详情页。他想知道的不是代码怎么写，而是：这个东西解决了什么问题、站主是怎么想的、技术上做了哪些取舍、最后做成了什么样。看完之后他应该能提出具体的技术问题，而不是只能问"这是做什么的"。

**Why this priority**: 项目是站主能力的直接证据，项目详情页是作品集的主体内容。它依赖 P1 提供的导航框架，但内容上完全独立。

**Independent Test**: 只发布一个项目的详情页并可从首页到达，检验读者读完能否复述该项目的目标、关键取舍与结果。

**Acceptance Scenarios**:

1. **Given** 访客位于项目列表，**When** 他选择一个项目，**Then** 进入该项目独立地址的详情页，页面包含：要解决的问题、方案概述、关键技术取舍、架构或流程图、运行截图、结果与现状、源代码仓库入口。
2. **Given** 访客读完项目详情，**When** 他查看代码，**Then** 页面提供可点击的源代码仓库地址。
3. **Given** 某项目不适合公开源代码，**When** 访客查看该项目，**Then** 页面正常呈现，源码入口处显示为不可用状态而非失效链接。
4. **Given** 站主新增一个项目，**When** 他完成发布，**Then** 全过程不需要修改任何页面代码，仅新增内容文件与素材即可。

---

### User Story 3 - 读者阅读一篇技术文章 (Priority: P3)

一位技术读者从搜索引擎或他人分享的链接直接进入某篇文章，他不了解站主，也不知道站点还有什么。他关心的是这篇文章能不能解决他当下的问题。读完后，他应该能顺着页面发现站主还有其他内容。

**Why this priority**: 技术文章是站点的第二个使命，也是吸引陌生读者的主要途径。它可以独立于项目区存在并产生价值。

**Independent Test**: 只发布一篇文章，从外部链接直接打开该文章，检验正文可正常阅读、地址可分享、且页面上能找到站点其余内容的入口。

**Acceptance Scenarios**:

1. **Given** 读者持有一篇文章的地址，**When** 他打开该地址，**Then** 正文完整呈现，包含标题、发布日期与正文内容。
2. **Given** 读者正在阅读一篇文章，**When** 他滚动或浏览页面，**Then** 可看到同站其他文章的入口。
3. **Given** 文章包含代码块、表格或图片，**When** 读者在移动端查看，**Then** 这些内容不产生整页横向滚动条。
4. **Given** 站主更新了某篇文章，**When** 读者再次访问原地址，**Then** 原地址依然有效并呈现最新内容。

---

### User Story 4 - 站主以纯文本方式发布与更新内容 (Priority: P4)

站主想更新站点时，不希望登录任何管理后台、打开浏览器编辑器或手工上传文件。他希望在本地用熟悉的文本编辑器写完，然后通过一次提交推送，站点自己就更新了。

**Why this priority**: 这是站点能否被长期维护的关键。如果每次发文章都要手工操作，站主会逐渐放弃更新，站点随之废弃。它不影响首次上线，但决定站点寿命。

**Independent Test**: 站主新增一篇文章并推送，检验站点是否在无需任何手工部署操作的情况下自动呈现该文章。

**Acceptance Scenarios**:

1. **Given** 站主在本地写好一篇新文章，**When** 他提交并推送，**Then** 站点在数分钟内自动呈现该文章，无需手工上传或执行部署命令。
2. **Given** 站主写了一篇尚未完成的草稿，**When** 他提交推送，**Then** 该草稿不对访客可见。
3. **Given** 站主想修正某篇文章的错别字，**When** 他提交推送，**Then** 该文章地址不变，内容更新。
4. **Given** 站主已有一批本地 Markdown 素材，**When** 他将其纳入站点，**Then** 正文无需重写即可呈现。

---

### User Story 5 - 读者订阅并发现站点内容 (Priority: P5)

一位技术读者认可站点的内容质量，希望以后能在自己的阅读器里直接看到新文章，不想反复手动访问。同时，另一位读者在搜索某个技术问题时，应该能搜到站点的相关文章。

**Why this priority**: 决定站点能否积累长期读者。缺少它站点仍可用，但读者会流失。

**Independent Test**: 订阅站点订阅源，发布一篇新文章，检验阅读器中是否出现该文章；并用搜索引擎检索文章标题，检验是否被收录。

**Acceptance Scenarios**:

1. **Given** 读者使用阅读器，**When** 他添加站点订阅地址，**Then** 能看到已有文章的标题与摘要，并在新文章发布后收到更新。
2. **Given** 一篇文章已发布一段时间，**When** 读者用搜索引擎检索其标题，**Then** 能找到该文章的地址。
3. **Given** 读者把某篇文章地址粘贴到社交平台，**When** 平台生成预览卡片，**Then** 卡片显示正确的标题、摘要与封面图。
4. **Given** 读者想找站内某个主题的内容，**When** 他使用站内检索输入关键词，**Then** 得到匹配的文章与项目列表；无匹配时得到明确的空结果提示。

---

### User Story 6 - 站主为项目附加可交互演示 (Priority: P6)

某个项目的静态页面预览比任何截图都有说服力，站主希望把它放到站点上让人直接点开试用。他希望在需要的时候能方便地加一个，不需要的时候站点上不出现任何痕迹。

**Why this priority**: 显著提升项目说服力，但不是所有项目都具备可演示形态，因此不是上线必需项。它必须在架构上"随时可加"，但不阻塞首期发布。

**Independent Test**: 为一个已发布项目配置演示入口，检验演示可正常打开；移除配置后，检验页面上不再出现该区域且不留空位。

**Acceptance Scenarios**:

1. **Given** 某个项目已配置可交互演示，**When** 访客打开该项目详情页，**Then** 页面上出现可交互的演示区域，并可全屏打开。
2. **Given** 某个项目未配置演示，**When** 访客打开该项目详情页，**Then** 页面上不出现演示区域，也不留下空白占位。
3. **Given** 演示内容加载失败或耗时过长，**When** 访客停留，**Then** 页面其余内容正常阅读，且访客能获得降级提示。
4. **Given** 站主想为项目加上演示，**When** 他完成发布，**Then** 不需要修改页面代码。

---

### User Story 7 - 海外读者访问站点 (Priority: P7)

站主将来可能面向海外岗位或海外技术社区，届时海外读者打开站点不应该出现长时间无响应。

**Why this priority**: 当前读者以国内为主，此项为未来扩展。它不应影响当前上线时间，但站点结构上不能把它排除在外。

**Independent Test**: 从海外网络位置访问站点，检验能否在常规等待时间内完成首屏呈现；并检验增加该线路后内容地址与页面结构均未改变。

**Acceptance Scenarios**:

1. **Given** 站点当前主要服务国内访客，**When** 站主决定增加面向海外的访问线路，**Then** 不需要修改任何内容或页面结构。
2. **Given** 站点已增加海外线路，**When** 海外访客打开原地址，**Then** 首屏在常规等待时间内可见。
3. **Given** 站点同时存在两条访问线路，**When** 任一线路出现故障，**Then** 另一线路的访客不受影响。

---

### Edge Cases

- 文章没有封面图时，列表与分享卡片应使用默认样式，不留破图。
- 项目没有可交互演示时，详情页不出现演示区域，也不留空白。
- 项目未开源、没有仓库地址时，详情页正常呈现，源码入口显示为不可用状态。
- 项目详情页的截图或演示体积较大时，页面其余内容应先于它们可读。
- 站主提交了未完成或不打算公开的内容时，该内容不得对访客可见。
- 文章地址在内容更新、标题修改后必须保持不变，避免已分享链接失效。
- 站内检索无匹配结果时，需给出明确提示而非空白页。
- 内容中出现已失效的外部链接或已下线的仓库时，站点其余部分不受影响。
- 移动端上出现宽表格、长代码行或宽截图时，不得导致整页横向滚动。
- 站点内容中不得出现任何凭证、密钥或第三方隐私信息（如抓取类项目中的账号配置）。
- 访客希望获取简历时，站点应引导其通过公开联系方式主动联络，站点上不得存在失效的简历下载入口。

## Requirements *(mandatory)*

### Functional Requirements

**身份与入口**

- **FR-001**: 站点 MUST 提供首页，包含站主身份说明、主要技术方向、精选项目入口、最新文章入口与联系方式。
- **FR-002**: 首页 MUST 在首屏（无需滚动）内呈现站主身份与至少一种联系方式。
- **FR-003**: 站点 MUST 提供"关于我"页面，包含个人简介、技能概览、工作经历与联系方式。
- **FR-004**: 站点 MUST NOT 公开站主的简历文件与手机号；简历仅在招聘方主动联系后单独提供。
- **FR-005**: 站点 MUST 在任意页面提供返回首页与联系站主的入口。
- **FR-006**: 站点 MUST 明确标示站主身份（姓名或稳定使用的标识），避免访客无法确认站点归属。

**项目**

- **FR-007**: 站点 MUST 提供项目列表，展示每个项目的名称、一句话说明、技术要点与当前状态。
- **FR-008**: 每个项目 MUST 拥有独立且稳定的详情页地址，包含：要解决的问题、方案概述、关键技术取舍、架构或流程图、运行截图、结果与现状。
- **FR-009**: 项目详情页 MUST 提供源代码仓库入口；当项目未开源时，该入口 MUST 呈现为不可用状态而非失效链接。
- **FR-010**: 项目详情页 MUST 支持一个可选的"可交互演示"区域；未配置时该区域 MUST 完全不出现。
- **FR-011**: 新增或修改一个项目 MUST 仅通过新增或编辑内容文件与素材完成，MUST NOT 要求修改页面代码。

**文章**

- **FR-012**: 站点 MUST 提供文章列表，按发布时间倒序展示标题、摘要与发布日期。
- **FR-013**: 每篇文章 MUST 拥有独立且稳定的地址，包含标题、发布日期与正文。
- **FR-014**: 文章正文 MUST 支持代码块、表格、图片与引用等常见技术写作元素，并在移动端不产生整页横向滚动。
- **FR-015**: 文章地址 MUST 在标题或内容更新后保持有效。
- **FR-016**: 阅读任一文章时，访客 MUST 能找到同站其他内容的入口。

**写作与发布**

- **FR-017**: 站点的全部内容（文章、项目、页面）MUST 以纯文本标记格式存放于版本库中。
- **FR-018**: 站主 MUST 能够在不登录任何管理后台的前提下完成内容发布。
- **FR-019**: 从内容提交到对外可见 MUST 由自动化流程完成，MUST NOT 需要手工上传文件或执行部署命令。
- **FR-020**: 站点 MUST 支持"草稿"状态，处于草稿状态的内容 MUST NOT 对外可见。
- **FR-021**: 站点 MUST 能直接承载现有的 Markdown 素材，正文 MUST NOT 需要重写。

**发现与订阅**

- **FR-022**: 站点 MUST 提供订阅源，读者可据此在阅读器中获取文章更新。
- **FR-023**: 站点 MUST 提供站点地图与页面元信息，使页面可被搜索引擎收录。
- **FR-024**: 站点 MUST 为每个页面提供分享预览信息（标题、摘要、封面），使社交平台能生成正确的预览卡片。
- **FR-025**: 站点 MUST 提供站内关键词检索，可检索文章与项目；无匹配结果时 MUST 给出明确提示。

**可访问性与可迁移性**

- **FR-026**: 站点 MUST 在移动端与桌面端均可正常阅读，MUST NOT 出现整页横向滚动。
- **FR-027**: 站点 MUST 为视觉阅读提供明暗两种显示模式。
- **FR-028**: 站点面向国内访客 MUST 在常规网络条件下于可接受时间内完成首屏呈现。
- **FR-029**: 站点 MUST 能够在不改动内容与页面地址的前提下更换托管位置。
- **FR-030**: 站点 MUST 能在不改动内容与页面结构的前提下增加一条面向海外的访问线路。

**边界与安全**

- **FR-031**: 站点 MUST NOT 包含用户注册、登录或任何依赖数据库的运行时能力。
- **FR-032**: 站点的公开内容 MUST NOT 包含凭证、密钥、令牌或第三方个人隐私信息。
- **FR-033**: 站点 MUST NOT 依赖任何需要按访问量付费、可能导致意外账单的组件。
- **FR-034**: 站点的内容与页面 MUST NOT 与特定托管服务商绑定，站主 MUST 能够自行决定托管位置。

**内容与隐私策略**

- **FR-035**: 面向海外读者 MUST 仅要求访问可达；站点内容 MUST NOT 要求提供中英双语版本。
- **FR-036**: 站点 MUST 公开至少一种有效联系方式（邮箱）与站主的公开技术账号；MUST NOT 公开手机号。

### Key Entities

- **文章（Article）**：一篇技术写作。关键属性：标题、摘要、发布日期、正文、可选封面、可选标签、草稿状态。每篇拥有稳定地址。
- **项目（Project）**：一个独立完成的工程作品。关键属性：名称、一句话说明、承担角色、技术要点、当前状态、源代码位置、可选的可交互演示入口，以及正文（问题、方案、取舍、架构、截图、结果）。每个项目拥有稳定地址。
- **页面（Page）**：无发布时间属性的固定内容，例如"关于我"。关键属性：标题、正文、地址。
- **素材（Asset）**：随内容一起发布的静态文件，包括架构图、截图与演示构建产物。简历文件不在其中。
- **订阅源（Feed）**：文章集合的机器可读视图，供阅读器消费。
- **站点配置（Site Config）**：站主标识、站点名称、导航结构、联系方式、默认分享信息。变更频率最低。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一位不了解站主的访客，能在 30 秒内从首页说出站主是谁、主要技术方向，并找到至少一种联系方式。
- **SC-002**: 访客从首页到达任一项目详情页，所需点击不超过 2 次。
- **SC-003**: 国内访客在常规宽带与 4G 网络下，首屏内容在 3 秒内可见。
- **SC-004**: 站主完成一次内容更新后，线上可见所需时间不超过 5 分钟，全程无需手工部署操作。
- **SC-005**: 新增一个项目所需的改动仅限内容文件与素材，页面代码改动为零。
- **SC-006**: 抽取 3 篇现有 Markdown 素材迁移上线，正文内容无丢失、无需重写。
- **SC-007**: 已发布的文章标题可被主流搜索引擎检索到，且分享链接时显示正确的标题、摘要与封面。
- **SC-008**: 站点在主流移动端与桌面端浏览器上均无整页横向滚动，正文可正常阅读。
- **SC-009**: 将站点从一处托管迁移到另一处，内容与页面地址不变，迁移操作在 1 小时内完成。
- **SC-010**: 订阅者在新文章发布后 1 小时内可从阅读器获取该文章。
- **SC-011**: 站内检索在 1 秒内返回结果或明确的空结果提示。
- **SC-012**: 站点上线后，站主每月用于站点维护（不含写作）的时间不超过 1 小时。
- **SC-013**: 站主可独立完成全部内容更新，不需要他人协助或额外学习成本。

## Assumptions

- **内容语言**：仅提供中文内容，不做双语；海外扩展只要求访问可达（见 FR-030、FR-035）。
- **内容来源**：现有素材——一个 B 站内容存档与直播录制工具、一个自选信源的技术资讯阅读方案、以及一篇网络排查记录——可直接作为首批内容。
- **首期范围**：首次上线包含首页、"关于我"、2 个项目与 1 篇文章；其余内容随后补齐。
- **单人维护**：站点由站主一人维护，无协作、审核或权限角色需求。
- **明确不做**：用户系统、评论、访问统计、付费内容、后台管理界面、数据库。评论与统计若将来需要，优先采用第三方托管服务而非自建。
- **演示形态**：可交互演示默认为静态页面形式；依赖常驻服务或私有凭证的项目不提供在线演示，改以截图或录屏呈现。
- **发布环境**：站主具备域名与国内云服务账号，内容发布依赖版本库托管服务。
- **技术选型**：具体框架、托管位置与部署方式属于规划阶段的决策，本规格不加以约束，仅要求满足 FR-029、FR-030、FR-033。
- **合规**：内容涉及第三方平台数据时，公开范围以不泄露凭证、不侵犯第三方隐私为底线；具体措辞由站主把关。
- **可用性目标**：站点面向小众读者（作品集与技术读者），不追求高并发；成功标准以单访客体验衡量。
