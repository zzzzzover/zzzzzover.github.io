# Phase 0 研究：个人作品集与技术博客站点

**Feature**: `001-portfolio-blog` | **Date**: 2026-09-12

本文件记录方案阶段的技术决策。每项决策给出选型、理由与被否决方案。约束来源为 `spec.md`（FR/SC 编号）与 `.specify/memory/constitution.md`。

---

## D1. 站点生成器：Astro

**决策**：使用 Astro，`output: 'static'`。

**理由**：

- 规格要求内容以纯文本标记存放于版本库（FR-017），且新增内容不得改动页面代码（FR-011）。Astro 的内容集合把 frontmatter 结构与渲染解耦，正好是这条需求的直接实现。
- 宪法 III 要求纯静态产物。Astro 默认输出静态文件，不需要服务和适配器。
- 规格 P6 要求"可交互演示随时可加"。Astro 允许在静态页面中按需插入任意前端框架组件，也允许直接嵌入 `public/` 下的独立产物，两条路径都保留。
- 主题生态成熟，满足"参考现有模板尽快上线"的诉求。

**被否决方案**：

| 方案 | 否决原因 |
|---|---|
| Hugo | 构建极快、主题多，但 Go 模板的调试与改动体验差；本项目需要自行实现项目页（User Story 2），改造成本高于 Astro |
| Hexo | 中文圈老牌，但生态老化、插件质量参差，长期维护风险高，与"单人长期维护"目标冲突 |
| Next.js | 规格无动态数据需求（FR-031 排除数据库与用户系统）。SSR/App Router 的心智负担与部署约束属纯增复杂度，违反宪法 I |
| VitePress | 为文档站设计，博客的信息架构与列表/标签需求要另行拼装，且会把站点带向文档思维 |
| WordPress / Ghost | 与 git 工作流直接冲突（FR-017、FR-018），并引入数据库与后台，同时违反宪法 I 和 III |

## D2. 主题基座：以 Astro Paper 为起点

**决策**：以 [satnaing/astro-paper](https://github.com/satnaing/astro-paper) 作为模板起点（fork 后纳入本仓库，而非作为依赖引入）。模板只承载全局框架与文章区；**项目列表与项目详情页自行实现**。

**理由**：

- 该模板定位为"极简、可访问、对搜索引擎友好"，与宪法 I 的取向一致。
- 开箱提供文章列表、文章页、明暗模式（FR-027）、RSS（FR-022）、sitemap（FR-023）、分享元信息（FR-024），这些本就是 P0/P5 范围内的已解决问题，自己重写只会推迟上线。
- 以模板（template）而非主题（package）方式引入，意味着代码进入本仓库由站主维护，不存在上游升级被锁死的问题，也避免"主题依赖"这一层额外抽象。

**被否决方案**：

| 方案 | 否决原因 |
|---|---|
| Fuwari | 功能更全、视觉更丰富，但引入 Svelte 运行时与更多前端资产，首屏 JS 预算（性能目标 ≤50 KB）更难守住，复杂度过高，违反宪法 I |
| 完全自建 | 需要重复实现 RSS、sitemap、搜索、明暗模式、SEO 元信息，直接推迟上线时间，与"尽快先上线"的需求冲突 |

**范围控制**：User Story 2 要求项目详情页讲清"问题 → 方案 → 取舍 → 结果"，这是作品集的门面，必须自行控制版式与信息层级，因此不复用模板的文章页布局，单独实现 `ProjectLayout.astro`。这条边界写进 `contracts/site-contract.md`，避免模板范围蔓延。

## D3. 站内检索：Pagefind

**决策**：使用 Pagefind，在 Astro 构建完成后对产物生成静态索引，由客户端按需加载。

**理由**：

- FR-025 要求站内关键词检索。内容为中文，中文没有词边界，通用全文检索方案在此处容易失效。Pagefind 对 CJK 采用 n-gram 处理（[Pagefind 多语言文档](https://pagefind.app/docs/multilingual/)），这是本项目能用全文检索的前提。
- 索引在构建后生成，按查询分片加载，不需要把全部正文下发到客户端，符合性能目标。
- 完全无服务端组件，符合宪法 III。

**被否决方案**：

| 方案 | 否决原因 |
|---|---|
| 不做搜索 | 直接违反 FR-025 |
| 仅标题与摘要的客户端模糊匹配 | 零依赖、最简，但检索不到正文关键词，对技术文章而言检索价值过低，等于名义上满足需求 |
| Fuse.js 全量索引 | 需把全部正文序列化下发到客户端，首屏体积与内容抓取成本都不可接受 |
| 任何托管的搜索服务 | 引入外部服务与潜在计费，违反宪法 III |

## D4. 发布自动化：服务端裸仓库 + post-receive 钩子

**决策**：在香港/新加坡轻量服务器上建立裸仓库，`post-receive` 钩子在工作区拉取最新提交、执行构建、把产物原子切换到 Caddy 的服务目录。

**理由**：

- FR-019 要求提交后自动上线，不得手工上传或执行部署命令。当前仓库尚无远程（站主明确要求暂不推送），CI 路径不可用，因此把构建放在服务器侧是目前唯一可落地的自动化方案。
- 发布逻辑只有一份 shell 脚本，落在本仓库的 `deploy/` 内受版本控制，站主可自行审查与修改。
- 与托管服务商零绑定：更换服务器只需重放同一份 `deploy/` 内容，符合 FR-029 与 FR-034。
- 原子切换（指向新的发布目录再改符号链接）保证发布过程中访问者不会看到半成品，也提供天然回滚点。

**被否决方案**：

| 方案 | 否决原因 |
|---|---|
| 本地构建 + rsync 上传 | 每次发布需手工执行命令，违反 FR-019 |
| GitHub Actions + rsync | 引入远程仓库、密钥与外部服务依赖；站主当前明确不推送远程。待将来添加远程后可作为**并行**发布路径加入，届时不需要改动站点内容与页面 |
| 服务器上运行 Node 常驻服务（SSR） | 直接违反宪法 III |

**遗留风险**：小规格轻量服务器（1–2 GB 内存）上执行构建需要足够内存。若构建失败，发布脚本必须保留上一个发布目录不切换，并在钩子输出中明确报错——这条写入 `contracts/site-contract.md`。

## D5. 图片与媒体处理

**决策**：需要参与构建优化的图片放在 `src/assets/`，由 Astro 内置图片能力生成多尺寸与现代格式；演示产物与不需要处理的静态文件放在 `public/`。媒体在纳入版本库前压缩，单篇内容嵌入媒体总量不超过 5 MB（宪法「内容与隐私约束」）。

**理由**：

- 截图与架构图是项目页的主要体积来源，直接决定首屏表现（SC-003）。
- 构建期处理不需要运行时组件，符合宪法 III。
- 5 MB 上限是可校验的硬约束，避免版本库与构建时间随内容增长失控。

**被否决方案**：

| 方案 | 否决原因 |
|---|---|
| 直接把原图放进 `public/` | 无尺寸与格式优化，移动端首屏不达标 |
| 引入外部图床 | 引入外部依赖与失效风险，且内容不再完全自持，与 FR-017 的取向不符 |
| 运行时图片处理 | 需要服务端组件，违反宪法 III |

## D6. 托管与 HTTPS（用户已确认）

**决策**：阿里云/腾讯云的香港或新加坡地域轻量应用服务器 + Caddy 提供静态服务与自动 HTTPS。

**理由**：

- 免 ICP 备案即可开通，满足"尽快上线"；用国内云账号与支付宝付款，与站主现有条件一致。
- 香港节点到国内延迟处于几十毫秒量级，能满足 SC-003 的首屏目标；海外读者也可直接访问，为 User Story 7 的扩展留出空间，不需要现在就做双线路。
- Caddy 自动申请与续期证书，把 HTTPS 的长期维护成本降到接近零，符合宪法 I。站主在 `tech-feed/deploy/` 已有 Caddy 使用经验，属复用而非新学。

**被否决方案**：

| 方案 | 否决原因 |
|---|---|
| Cloudflare Pages / Vercel 免费档 | 无需付费方式即可注册，静态请求免费不限量（[Cloudflare Pages 定价](https://developers.cloudflare.com/pages/functions/pricing/)），但绑自定义域名后国内访问质量不稳定。站点首要读者在国内，面试官打不开即为致命 |
| 国内轻量服务器 + 备案 | 国内速度最优，但备案需 1–2 周且是外部流程，直接阻塞上线；作为将来优化项保留 |
| 国内对象存储 + CDN | 阿里云 OSS 官方文档明确：默认域名与传输加速域名访问 `text/html` 会被强制下载，必须绑定已完成 ICP 备案的自定义域名才能正常预览（[阿里云 OSS 文档](https://www.alibabacloud.com/help/zh/oss/how-to-ensure-an-object-is-previewed-when-you-access-the-object)）。备案是硬性前置，同样阻塞上线 |

## D7. 运行时与依赖清单

**决策**：Node.js 22 LTS；运行期依赖共 5 项：`astro`、`@astrojs/rss`、`@astrojs/sitemap`、`pagefind`、`tailwindcss`（随模板引入）。

**理由**：依赖数量本身是宪法 I 的可校验指标。每一项都对应一条明确的功能需求，没有仅因"方便"而引入的包。

| 依赖 | 对应需求 | 若移除会损失什么 |
|---|---|---|
| `astro` | FR-011、FR-017、FR-029 | 站点无法构建 |
| `@astrojs/rss` | FR-022 | 需要自行序列化订阅源 |
| `@astrojs/sitemap` | FR-023 | 需要自行生成站点地图 |
| `pagefind` | FR-025 | 站内检索不可用（见 D3） |
| `tailwindcss` | FR-026、FR-027 | 需要自行实现样式系统；随模板引入，移除成本高于保留 |

**被否决方案**：引入任何 CMS、评论、统计、图标库、动画库或组件库。理由：均无对应功能需求，且会同时增加首屏体积与长期维护面。
