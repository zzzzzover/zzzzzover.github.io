# Phase 0 研究：个人作品集与技术博客站点

**Feature**: `001-portfolio-blog` | **Date**: 2026-09-12

本文件记录方案阶段的技术决策。每项决策给出选型、理由与被否决方案。约束来源为 `spec.md`（FR/SC 编号）与 `.specify/memory/constitution.md`。

---

## D1. 站点生成器：Astro

**决策**：使用 Astro，`output: 'static'`。

**理由**：

- 规格要求内容以纯文本标记存放于版本库（FR-017），且新增内容不得改动页面代码（FR-011）。Astro 的内容集合把 frontmatter 结构与渲染解耦，正好是这条需求的直接实现。
- 宪法 III 要求纯静态产物。Astro 默认输出静态文件，不需要服务和适配器。
- 规格 P6 要求"可交互演示随时可加"。Astro 允许在静态页面中按需插入任意前端框架组件，也允许直接嵌入 `public/` 下的独立产物，两条路径都保留。
- 主题生态成熟，满足"参考现有模板尽快上线"的诉求。

**被否决方案**：

| 方案 | 否决原因 |
|---|---|
| Hugo | 构建极快、主题多，但 Go 模板的调试与改动体验差；本项目需要自行实现项目页（User Story 2），改造成本高于 Astro |
| Hexo | 中文圈老牌，但生态老化、插件质量参差，长期维护风险高，与"单人长期维护"目标冲突 |
| Next.js | 规格无动态数据需求（FR-031 排除数据库与用户系统）。SSR/App Router 的心智负担与部署约束属纯增复杂度，违反宪法 I |
| VitePress | 为文档站设计，博客的信息架构与列表/标签需求要另行拼装，且会把站点带向文档思维 |
| WordPress / Ghost | 与 git 工作流直接冲突（FR-017、FR-018），并引入数据库与后台，同时违反宪法 I 和 III |

## D2. 主题基座：以 Astro Paper 为起点

**决策**：以 [satnaing/astro-paper](https://github.com/satnaing/astro-paper) 作为模板起点（fork 后纳入本仓库，而非作为依赖引入）。模板只承载全局框架与文章区；**项目列表与项目详情页自行实现**。

**实测基线**：版本 v6.1.0，commit `35cfa7f`，MIT 许可。已实际拉取、安装、构建、预览验证，
结论见 `verify.md`。构建 45 页 / 9.6 秒；首页首屏 gzip 后约 22 KB。

**理由**：

- 该模板定位为"极简、可访问、对搜索引擎友好"，与宪法 I 的取向一致。
- 开箱提供文章列表、文章页、明暗模式（FR-027）、RSS（FR-022）、sitemap（FR-023）、分享元信息（FR-024），这些本就是 P0/P5 范围内的已解决问题，自己重写只会推迟上线。
- 以模板（template）而非主题（package）方式引入，意味着代码进入本仓库由站主维护，不存在上游升级被锁死的问题，也避免"主题依赖"这一层额外抽象。

**被否决方案**：

| 方案 | 否决原因 |
|---|---|
| Fuwari | 功能更全、视觉更丰富，但引入 Svelte 运行时与更多前端资产，首屏 JS 预算（性能目标 ≤50 KB）更难守住，复杂度过高，违反宪法 I |
| 完全自建 | 需要重复实现 RSS、sitemap、搜索、明暗模式、SEO 元信息，直接推迟上线时间，与"尽快先上线"的需求冲突 |

**范围控制**：User Story 2 要求项目详情页讲清"问题 → 方案 → 取舍 → 结果"，这是作品集的门面，必须自行控制版式与信息层级，因此不复用模板的文章页布局，单独实现 `ProjectLayout.astro`。这条边界写进 `contracts/site-contract.md`，避免模板范围蔓延。

## D3. 站内检索：Pagefind（模板已内置）

**决策**：使用 Pagefind。**这是模板 AstroPaper 自带的能力，不是本项目另行引入的依赖**——模板的
`build` 脚本已包含 `pagefind --site dist` 步骤，检索页 `src/pages/search.astro` 也已就绪。

**理由**：

- FR-025 要求站内关键词检索。内容为中文，中文没有词边界，通用全文检索方案在此处容易失效。Pagefind 对 CJK 采用 n-gram 处理（[Pagefind 多语言文档](https://pagefind.app/docs/multilingual/)），这是本项目能用全文检索的前提。**实测确认**：加入中文内容后 Pagefind 自动识别语言为 `zh` 并正常建索引（见 `verify.md`）。
- 索引在构建后生成，按查询分片加载，不需要把全部正文下发到客户端，符合性能目标。
- 完全无服务端组件，符合宪法 III。

**修订说明**：草案阶段曾把 Pagefind 列为"需在宪法 I 下额外论证的复杂度"。实测发现它随模板而来，
无需额外引入，该论证已撤销，`plan.md` 的复杂度登记表同步更新。

**被否决方案**：

| 方案 | 否决原因 |
|---|---|
| 不做搜索 | 直接违反 FR-025 |
| 仅标题与摘要的客户端模糊匹配 | 零依赖、最简，但检索不到正文关键词，对技术文章而言检索价值过低，等于名义上满足需求 |
| Fuse.js 全量索引 | 需把全部正文序列化下发到客户端，首屏体积与内容抓取成本都不可接受 |
| 任何托管的搜索服务 | 引入外部服务与潜在计费，违反宪法 III |

## D4. 发布自动化：服务端裸仓库 + post-receive 钩子

**决策**：在香港/新加坡轻量服务器上建立裸仓库，`post-receive` 钩子在工作区拉取最新提交、执行构建、把产物原子切换到 Caddy 的服务目录。

**理由**：

- FR-019 要求提交后自动上线，不得手工上传或执行部署命令。当前仓库尚无远程（站主明确要求暂不推送），CI 路径不可用，因此把构建放在服务器侧是目前唯一可落地的自动化方案。
- 发布逻辑只有一份 shell 脚本，落在本仓库的 `deploy/` 内受版本控制，站主可自行审查与修改。
- 与托管服务商零绑定：更换服务器只需重放同一份 `deploy/` 内容，符合 FR-029 与 FR-034。
- 原子切换（指向新的发布目录再改符号链接）保证发布过程中访问者不会看到半成品，也提供天然回滚点。

**被否决方案**：

| 方案 | 否决原因 |
|---|---|
| 本地构建 + rsync 上传 | 每次发布需手工执行命令，违反 FR-019 |
| GitHub Actions + rsync | 引入远程仓库、密钥与外部服务依赖；站主当前明确不推送远程。待将来添加远程后可作为**并行**发布路径加入，届时不需要改动站点内容与页面 |
| 服务器上运行 Node 常驻服务（SSR） | 直接违反宪法 III |

**遗留风险**：小规格轻量服务器（1–2 GB 内存）上执行构建需要足够内存。若构建失败，发布脚本必须保留上一个发布目录不切换，并在钩子输出中明确报错——这条写入 `contracts/site-contract.md`。

## D5. 图片与媒体处理

**决策**：需要参与构建优化的图片放在 `src/assets/`，由 Astro 内置图片能力生成多尺寸与现代格式；演示产物与不需要处理的静态文件放在 `public/`。媒体在纳入版本库前压缩，单篇内容嵌入媒体总量不超过 5 MB（宪法「内容与隐私约束」）。

**理由**：

- 截图与架构图是项目页的主要体积来源，直接决定首屏表现（SC-003）。
- 构建期处理不需要运行时组件，符合宪法 III。
- 5 MB 上限是可校验的硬约束，避免版本库与构建时间随内容增长失控。

**被否决方案**：

| 方案 | 否决原因 |
|---|---|
| 直接把原图放进 `public/` | 无尺寸与格式优化，移动端首屏不达标 |
| 引入外部图床 | 引入外部依赖与失效风险，且内容不再完全自持，与 FR-017 的取向不符 |
| 运行时图片处理 | 需要服务端组件，违反宪法 III |

## D6. 托管与 HTTPS（用户已确认）

**决策**：阿里云/腾讯云的香港或新加坡地域轻量应用服务器 + Caddy 提供静态服务与自动 HTTPS。

**理由**：

- 免 ICP 备案即可开通，满足"尽快上线"；用国内云账号与支付宝付款，与站主现有条件一致。
- 香港节点到国内延迟处于几十毫秒量级，能满足 SC-003 的首屏目标；海外读者也可直接访问，为 User Story 7 的扩展留出空间，不需要现在就做双线路。
- Caddy 自动申请与续期证书，把 HTTPS 的长期维护成本降到接近零，符合宪法 I。站主在 `tech-feed/deploy/` 已有 Caddy 使用经验，属复用而非新学。

**被否决方案**：

| 方案 | 否决原因 |
|---|---|
| Cloudflare Pages / Vercel 免费档 | 无需付费方式即可注册，静态请求免费不限量（[Cloudflare Pages 定价](https://developers.cloudflare.com/pages/functions/pricing/)），但绑自定义域名后国内访问质量不稳定。站点首要读者在国内，面试官打不开即为致命 |
| 国内轻量服务器 + 备案 | 国内速度最优，但备案需 1–2 周且是外部流程，直接阻塞上线；作为将来优化项保留 |
| 国内对象存储 + CDN | 阿里云 OSS 官方文档明确：默认域名与传输加速域名访问 `text/html` 会被强制下载，必须绑定已完成 ICP 备案的自定义域名才能正常预览（[阿里云 OSS 文档](https://www.alibabacloud.com/help/zh/oss/how-to-ensure-an-object-is-previewed-when-you-access-the-object)）。备案是硬性前置，同样阻塞上线 |

## D7. 运行时与依赖清单

**决策**：Node.js ≥ 22.12.0（模板 `engines` 要求，实测用 22.23.2 通过）；沿用模板 AstroPaper v6
的既有依赖，不额外引入任何包。

**实测数据**：模板顶层声明 **25 个包**，`pnpm install` 实际安装 **554 个包**（含传递依赖），
安装耗时 47.8 秒。核心为 Astro 7.0.3、Tailwind 4.3.2、TypeScript 6.0.3、sharp 0.35.2。

**修订说明**：草案阶段声称"运行期依赖共 5 项"，这是**不准确的**——它只覆盖了本项目主动选择的部分，
忽略了模板自带的一整套工具链。真实情况如上。这不构成对宪法 I 的违反（这些依赖随模板而来，移除
它们的成本高于保留），但**数量必须被如实记录**，否则"依赖数量是简约优先的可校验指标"这句话就是空的。

**仍然明确不引入**：任何 CMS、评论、统计、图标库、动画库或组件库。理由：均无对应功能需求，且会
同时增加首屏体积与长期维护面。

**必须移除的构建期外部依赖**：模板原配置在构建时从 Google Fonts 并发抓取 20 个字体文件，失败即
整个构建失败且无重试。**该依赖已移除**，详见 D8。

## D8. 字体策略：站点用系统字体栈，分享图用本地子集字体（实测后两次修订）

**决策（两部分，互不相关，不要混淆）**：

1. **站点正文字体**：移除模板的 Google Fonts 构建期抓取，改用**系统字体栈**（含 PingFang SC /
   Microsoft YaHei / Noto Sans CJK SC）。
2. **分享图字体**：**保留动态分享图**，字体用随仓库提交的**中文字体子集**，构建期从本地文件读取。

**第 1 部分的理由**：

- 模板原配置在构建时并发抓取 20 个 Google Fonts 文件。**实测连续两次构建失败，且两次挂在不同
  文件上**；同一 URL 用 `curl` 单独请求却返回 200。这不是"不可达"而是"并发抓取不稳定"，会**随机**
  导致发布失败，且模板无重试。对"推送即发布"的流水线，后果是静默不发布。
- 系统字体栈对中文阅读观感通常更好，且彻底消除构建期网络依赖，直接服务于 SC-004（发布可靠）。

**第 2 部分的理由（实测）**：初版决策曾把动态分享图一并关闭，理由是"中文字体体积 5–20 MB 不适合
进构建产物"。**该判断经实测证伪**：

| 实测项 | 结果 |
|---|---|
| 子集字体（仅一张卡片实际用字） | 33 KB |
| 子集字体（+3000 常用汉字） | **821 KB** |
| satori 渲染单张 1200×630 | 22–45 ms |
| sharp 转 PNG | 26–225 ms |
| 输出 PNG | 57 KB |
| **渲染内存增量** | **+9 MB（33KB 字体）／+11 MB（821KB 字体）** |

关键结论：**字体体积对内存几乎无影响**（基线 211 MB 是 Node + sharp 自身）。原先"中文字体会拖垮
小服务器"的担心不成立。因此没有理由为省几百 KB 而牺牲每篇独立的分享卡片。

**实测撞到的三个坑（实现时必须绕开）**：

1. **satori 不能读 `.ttc` 集合**：系统中文字体均为 `.ttc`（Noto Sans CJK，18–27 MB 内装十个字重），
   直接喂入报 `Unsupported OpenType signature`。
2. **satori 不能读可变字体**：`NotoSansSC[wght].ttf` 触发内部 `parseFvarAxis` 崩溃。必须使用
   **静态实例**。
3. **缺字是静默失败**：子集未覆盖的字符**直接消失留空白**，不报错、也不显示豆腐块。实测中
   「用 未覆盖字符测试 修复 黑洞 犇龘靐齉」只渲染出「用 修复 黑洞」。**因此必须有构建期覆盖检查。**

**子集字体的生成方式**：

- 工具：`subset-font`（harfbuzz wasm，纯 JS，无原生依赖）
- 必须带 `variationAxes: { wght: 400 }` 完成可变字体实例化，否则输出仍为可变字体
- 覆盖范围：站点信息 + 全部内容标题与描述的字符 + 3000 常用汉字，产物约 **821 KB**
- 产物提交进仓库：`src/assets/fonts/og-subset.ttf` 与字符覆盖清单
- 生成脚本为**开发期工具**，不进构建流程、不上服务器

**被否决方案**：

| 方案 | 否决原因 |
|---|---|
| 保留 Google Fonts 原样 | 构建随机失败；`site-contract.md` 规定"失败不切换线上"，结果是静默不发布 |
| 关闭动态分享图，全站共用一张默认图 | **已撤销**。实测证明代价被高估，且站主明确要求每篇独立卡片 |
| 提交完整静态中文字体（8–10 MB） | 体积是子集方案的十倍以上，收益仅是省掉一次开发期生成步骤 |
| 用 fonttools 子集化 | 属 pip 生态，需在开发机或服务器额外装 Python 环境；harfbuzz 方案零额外环境 |
| 用 fontkit 子集化 | **实测其输出签名非法**（`01000404`，合法 TTF 应为 `00010000`），satori 拒绝 |
| 换掉 satori 用别的渲染路径 | 需重新验证整套方案，成本远高于绕开上述三个坑 |
| 自建图片生成服务 | 需要服务端运行时，直接违反宪法 III |

**代价（已接受）**：

- 仓库多约 821 KB 二进制（字体）加一个字符覆盖清单
- 内容引入生僻字时需重跑一次生成脚本——但构建期覆盖检查会明确指出是哪个字、来自哪篇内容
- 每篇文章在构建期多生成一张 PNG（单张约 270 ms；完整站点上的实际增量需实测）
- 仅用 `wght: 400` 单一字重，卡片标题的粗体由 satori 合成；若观感不满意需再生成 700 子集
  （体积约翻倍）

**仍然保持**：构建期零外部网络请求——字体是仓库里的文件，生成脚本只在开发期运行。

## 已确认的后续决策（模板验证之后）

- **文章路由**：沿用模板的 `/posts/`，不采用草案中的 `/writing/`。相应的契约与数据模型已修订。
- **字体**：站点正文用系统字体栈；分享图用仓库内的中文子集字体，动态分享图**保留**。见 D8。
- **分享图方案**：子集字体 + 构建期字符覆盖检查；覆盖范围为 +3000 常用汉字（约 821 KB）。
- **分享目标**：精简为中国读者常用（微信、邮箱、复制链接），替换模板默认的
  whatsapp / facebook / x / telegram / pinterest。

无。`spec.md` 中的两处 `[NEEDS CLARIFICATION]` 已由站主确认为：海外扩展仅要求访问可达、不做双语；公开邮箱与公开技术账号、不公开手机号与简历。`plan.md` 的技术上下文中无 `NEEDS CLARIFICATION`。
