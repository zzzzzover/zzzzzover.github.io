## 要解决的问题

用 App 刷技术内容有三个绕不开的毛病：

| 毛病 | 具体表现 |
|---|---|
| 看到什么由算法决定 | 平台目标是让你多停留，不是让你学到东西 |
| 注水内容泛滥 | 标题党、大段废话、结尾引流、机器批量生成 |
| 广告混进内容里 | 伪装成文章的原生广告，和真实内容长得一样 |

根因是**信息流的准入权不在自己手里**。所以这个项目换了一条路：不看推荐，只订阅。

## 方案概述

三个互相独立的环节，中间用文件衔接：

```
你维护信源清单          机器生成订阅文件            你在阅读器里读
data/sources.yaml  ──►  dist/tech-feed.opml  ──►  Inoreader（免费档）
（唯一要手改的地方）      （自动生成，不用碰）
```

再配一个每月跑一次的体检脚本，报告哪些源打不开了、哪些停更了。
工具链是**纯 Python 标准库**——没有依赖，因此几年后也不会因为包管理环境变化而跑不起来。

## 关键技术取舍

**1. 清单与阅读器解耦。**
订阅文件（OPML）是标准格式，阅读器只是消费者。哪天不想用现在这个阅读器，换一个只要重新导入
一次，清单本身不用动。这是整个设计里最重要的一条：**把选择的自由留在自己手里**。

**2. 噪声在「挑选」环节挡掉，而不是在「阅读」环节过滤。**
大部分方案试图在读完之前做过滤（关键词屏蔽、AI 摘要）。但过滤永远滞后于生产。
这个项目把成本前移到信源准入：进清单之前先按一套写好的标准过一遍
（见 `docs/admission-criteria.md`）。清单小，噪声就少。

**3. 不做抓取与存储，只生成订阅文件。**
早期版本考虑过自建抓取 + 入库 + 自建前端。放弃的原因是：那会引入常驻服务、数据库与
内容版权风险，而收益只是"已读状态在自己手里"——用订阅文件换不来这个收益时，
它不构成理由。**这个取舍后来被证明是需要重新评估的**，见下文。

**4. 验收标准不用"好不好用"，而用可测的指标。**
项目的验收标准（AC-1 … AC-7）包括：订阅文件能被阅读器正常导入、多端已读同步可用、
广告形态是否可接受、月度巡检能正确识别失效源。全部通过才认为方向成立。

## 架构

```
                  ┌─────────────────────────────┐
   data/          │  tools/                     │
   sources.yaml ──►  build_opml.py  ──► dist/tech-feed.opml
   （唯一手改）    │  healthcheck.py ──► reports/（月度巡检）
                  │  check_miniflux.py（自建方案探测）
                  │  demo.py         ──► demo/index.html（本地预览）
                  └─────────────────────────────┘
                              │
                              └──► 阅读器（可替换）

   deploy/  Caddyfile + docker-compose（自建服务器备用方案）
```

## 结果与现状

**状态：本方向已完成并验收。** 验收标准 AC-1 … AC-7 全部通过，262 项自测通过，
已在阅读器免费档上跑通：导入订阅、多端已读同步、广告形态可接受。
订阅文件可导出、可迁移。

## 一个被明确记录的失败判断

项目完成时得出的结论不是"方案很好"，而是记录了三项**换不掉的固有代价**：

1. **已读状态被服务商锁住**，无法导出——迁移能力仍然是假的
2. **源内过滤在付费墙后**，噪声只能靠挑选，不能靠过滤
3. **加工层不在自己手里**，想加自己的处理逻辑没有落点

因此另开分支做"不用现成阅读器"的方案，需求来源就是这三条。
**把"方案合格"和"方向还有代价"分开记下来，比只记成功更有用**——它让下一步有明确依据，
而不是凭感觉重开一局。
