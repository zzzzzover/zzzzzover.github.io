## 要解决的问题

想长期追的几个 UP 主，内容会消失：动态被删、视频下架、直播播完就没有回放。
手工保存不现实——你不知道他什么时候开播，也不知道哪条动态会被删。

需求可以拆成三件独立的事：**动态要增量留档、新视频要自动下载、直播要能自动录**。
三件事的触发条件不同（轮询、新动态、开播），失败模式也不同，因此不应该耦合在一起。

## 方案概述

一个常驻的轮询器，每 15 分钟检查一次目标 UP 主的状态，按需触发三类动作：

- **动态存档**：增量写入 `data/{uid}/dynamics.json`，只追加新条目
- **视频下载**：检测到新的视频动态时调用 `yt-dlp` 下载
- **直播录制**：检测到开播则启动独立录制进程，下播自动停止

开播与下播通过飞书推送通知，不需要盯着。

## 关键技术取舍

**1. 直播流直接 pipe 存盘，不做转码。**
B 站直播是 HTTP FLV 流。常见做法是喂给 ffmpeg 转封装，但这里直接把响应流 pipe 到 `.flv`
文件——**零 CPU 开销**，也不引入 ffmpeg 这个运行时依赖（只在视频下载路径上用）。
代价是文件必须用支持 FLV 的播放器（VLC / mpv / ffplay），不能直接塞进浏览器。

**2. 录屏跑在独立进程里，不依赖调度器存活。**
最初把录制放在轮询进程内，结果轮询重启（或 cron 会话结束）会把正在进行的录制一起带走。
改成 `fork` 出独立进程后，录制与轮询解耦：轮询只负责"发现开播"和"发现下播"。

**3. 断流用指数退避重连，而不是立即放弃。**
直播流的网络抖动很常见，直接判定"下播"会得到一堆几十秒的碎片文件。
改成最多 20 次指数退避重连；只有连续失败到上限才认为是真的结束了。

**4. 长直播自动分段（默认 60 分钟）。**
单文件过大会让后续处理（转写、检索）变得不现实，而直播常常持续数小时。

**5. 增量状态落盘，而不是每轮全量比对。**
动态列表接口返回的是全量，靠 `downloaded.json` / `seen.json` 记录已处理项来做增量。
代价是状态文件损坏时需要手工修——这是有意接受的：全量重下比丢数据更糟。

## 架构

```
轮询器（每 15 分钟）
  ├── 拉取 UP 主动态列表 ──► 增量写入 data/{uid}/dynamics.json
  │        └── 发现新视频 → 调用 yt-dlp 下载 → 记录 downloaded.json
  └── 查询直播状态
           └── 开播 → fork 独立录制进程
                        ├── HTTP FLV 流 → pipe → 分段 .flv
                        ├── 断流 → 指数退避重连（≤20 次）
                        ├── 每 60 分钟切分新文件
                        └── 下播 → 停止并写 meta.json / state.json
                                    └── 通知（飞书）
```

## 结果与现状

**状态：运行中。**

- 动态与视频存档按预期增量工作
- 直播录制在无人值守下可用：开播自动起录、下播自动停、断流能自恢复
- 长直播产生分段文件，便于后续单独处理

## 已知问题与后续方向

- **转写链路尚未定型**：仓库里有两条转写脚本（`transcribe.py` 与 `transcribe_funasr.py`），
  分别对应不同的语音识别方案，没有收敛到一条
- **没有任何 Web 界面**：全部产物是文件系统上的文件，检索与浏览依赖手工
- **凭证集中**：`.env` 与 `config.json` 同时承载 cookie 与推送 webhook，
  这是公开内容时需要格外小心的部分
