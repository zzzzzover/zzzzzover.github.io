# 个人作品集与技术博客站点 Constitution

## Core Principles

### I. 简约优先（Simplicity First）

本站的复杂度上限 MUST 低于站内所展示的项目本身。站点的价值来自内容，不来自实现。

非协商规则：

- 任何新增依赖、组件、抽象层或构建步骤，MUST 先回答"删掉它会损失什么"；无法回答则 MUST NOT 加入。
- 站点 MUST NOT 引入需要长期运维负担的组件（自建数据库、消息队列、容器编排等）。
- 每次方案评审 MUST 检查是否存在更简单的等价方案；引入的复杂度 MUST 被显式论证。

理由：本站由一人维护，且维护者同时是唯一的作者。复杂度是内容持续产出的直接敌人。

### II. 内容与渲染分离（Content-Render Separation）

内容的增减 MUST NOT 要求改动页面代码。

非协商规则：

- 新增一篇文章或一个项目 MUST 仅通过新增内容文件与素材完成，页面代码改动 MUST 为零。
- 全部内容 MUST 以纯文本标记格式存放于版本库；MUST NOT 依赖任何管理后台或数据库。
- 页面 MUST 对内容缺省项（无封面、无仓库地址、无演示）作出降级呈现，MUST NOT 出现破图或空占位。
- 可选能力（如可交互演示）MUST 通过内容侧的声明式配置启用。

理由：这是站点能否被长期维护的决定性条件。任何"发一篇文章要改代码"的设计都会导致站点废弃。

### III. 无运行时依赖（No Runtime Dependencies）

站点 MUST 是纯静态产物，运行时不依赖任何服务端逻辑。

非协商规则：

- 站点 MUST NOT 包含用户注册、登录、会话或任何服务端数据存储。
- 站点 MUST NOT 依赖按访问量计费、可能产生意外账单的服务。
- 动态能力（评论、访问统计等）如确需引入，MUST 优先采用第三方托管服务，MUST NOT 自建。
- 内容与页面地址 MUST NOT 与特定托管服务商绑定；站点 MUST 能在不改动内容的前提下更换托管位置。

理由：无运行时意味着无人值守也不会失效，迁移成本恒定为零。这与"少维护"的目标直接对齐。

## 内容与隐私约束

- 公开内容 MUST NOT 包含凭证、密钥、令牌或第三方个人隐私信息；引用现有项目素材时 MUST 逐项核对配置文件与截图。
- 站点 MUST 公开邮箱与公开技术账号；MUST NOT 公开手机号与简历文件。简历仅在招聘方主动联系后单独提供。
- 站主身份 MUST 在站点上明确标示；访客 MUST 能在任意页面找到联系方式。
- 内容仅提供中文版本，MUST NOT 维护双语正文；面向海外的扩展仅要求访问可达。
- 面向国内访客，站点 MUST 在常规宽带与移动网络下于 3 秒内呈现首屏。
- 媒体素材 MUST 在纳入版本库前压缩；单篇内容的嵌入媒体总量 SHOULD 不超过 5 MB。
- 涉及第三方平台数据的项目，公开范围 MUST 以不泄露凭证、不侵犯第三方隐私为底线。

## 开发与发布工作流

- 内容全部经版本库提交发布；从提交到线上可见 MUST 由自动化流程完成，MUST NOT 需要手工部署操作。
- 未完成内容 MUST 以草稿状态存在，草稿 MUST NOT 对外可见。
- 已发布内容的地址 MUST 保持稳定；标题与正文的修订 MUST NOT 改变地址。
- 工作按 Speckit 流程推进：需求 → 方案 → 任务 → 实现；每阶段产出 MUST 可独立验收。
- 每个用户故事 MUST 可独立上线并产生价值；首期范围 MUST 保持最小，先打通发布链路，再补齐内容。
- 涉及站点结构、内容模型或托管方式的变更 MUST 在方案阶段声明其对本宪法的合规性。

## Governance

- 本宪法优先于其他一切开发实践与个人习惯。与本宪法冲突的方案 MUST 被否决，或先修订本宪法。
- 修订 MUST 以文档形式提出，说明动机、影响范围与迁移方式，修订后 MUST 更新版本号。
- 版本号遵循语义化版本：原则的删除或重定义 → MAJOR；新增原则或实质性扩展 → MINOR；措辞澄清与非语义修订 → PATCH。
- 每次方案与实现阶段 MUST 校验合规性；复杂度相关决策 MUST 被显式论证。
- 运行时开发指导以本文件为准。若与其他文档冲突，以本文件为准，并修订冲突文档。
